# 单机运行容器合并决策

## 生效规格

- 原基线：V3.13 第 3、15、20、25 章
- 新基线：V3.14 修订说明及上述章节

## 当前问题

当前默认部署为每个后台角色创建一个容器，共二十个常驻 LongInvest 容器。虽然后端
镜像已经共享，但容器列表、部署重建和运行检查仍然冗长，不适合当前单机规模。

## 方案对比

1. 保持二十个容器：权限和资源边界最清楚，但单机运维复杂。
2. 所有后台合成一个进程：容器最少，却会让慢任务阻塞实时任务，破坏通知渠道、历史
   采集和策略沙箱的失败隔离。
3. 合并容器但保留独立进程：普通后台、策略回测、历史采集分为三组，每个任务角色
   仍使用独立进程和队列，由组内监督进程负责重启和健康检查。

## 决定

采用方案三，默认保留七个常驻容器。普通后台不挂载 Docker Socket；策略与回测后台
单独获得策略运行权限；历史采集继续使用浏览器专用镜像。旧逐进程模式只作为显式
故障排查模式，不与默认模式同时运行。

## 验收

2026-07-28 在服务器完成验收：

- 默认 Compose 启动七个常驻容器，API、前端、数据库、Redis 和三组后台均正常。
- 普通后台十一角色、策略后台四角色全部存活，队列和通知渠道映射保持不变。
- 主动结束维护角色后，该角色进程编号从 10 变为 359，其他角色和容器没有重启，
  容器健康检查持续通过。
- 日线队列在合并后继续领取任务；历史采集保持独立运行。
- 服务器测试容器完整执行 2187 项后端测试并全部通过，33 项按环境条件跳过。
- 繁忙日线任务期间七个容器总内存采样约 1.30 GiB。合并只降低容器运维数量，未减少
  任务进程；普通后台内存上限设为 1.5 GiB，以容纳多个工作子进程同时运行的峰值。
