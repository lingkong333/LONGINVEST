# 单机运行容器合并决策

## 生效规格

- 原基线：V3.13 第 3、15、20、25 章
- 新基线：V3.14 修订说明及上述章节

## 当前问题

当前默认部署为每个后台角色创建一个容器，共二十个常驻 LongInvest 容器。虽然后端
镜像已经共享，但容器列表、部署重建和运行检查仍然冗长，不适合当前单机规模。

## 方案对比

1. 保持二十个容器：权限和资源边界最清楚，但单机运维复杂。
2. 所有后台合成一个进程：容器最少，却会让慢任务阻塞实时任务，破坏通知渠道、历史
   采集和策略沙箱的失败隔离。
3. 合并容器但保留独立进程：普通后台、策略回测、历史采集分为三组，每个任务角色
   仍使用独立进程和队列，由组内监督进程负责重启和健康检查。

## 决定

采用方案三，默认保留七个常驻容器。普通后台不挂载 Docker Socket；策略与回测后台
单独获得策略运行权限；历史采集继续使用浏览器专用镜像。旧逐进程模式只作为显式
故障排查模式，不与默认模式同时运行。

## 验收

- 默认 Compose 只启动七个常驻容器。
- 每个既有角色均有独立子进程，队列和通知渠道映射不变。
- 停止单个子进程后，监督进程能够自动恢复该角色。
- API、前端、数据库、Redis 和三组后台健康检查通过。
- 实时任务、普通后台任务、策略任务和历史任务各完成一个代表性验证。
