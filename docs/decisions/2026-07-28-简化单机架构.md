# 简化单机架构设计决定

## 生效规格和范围

- 生效规格：V4.0 第 3、15、20、25.3～25.7、25.13、25.15、25.17～25.19 节。
- 涉及范围：任务执行、调度、数据采集、通知、策略沙箱、回测、健康检查和 Docker 部署。

## 问题

V3.15 将单机 MVP 拆成 Redis、RQ、分发器、看门狗、维护进程、监督进程以及多种常驻 Worker。实际使用中，一个全市场任务还会展开为数千个通用单股任务。这增加了常驻服务数量、内存占用、任务状态和锁竞争，也让故障定位跨越过多中间层。

产品的实际规模是单管理员、单服务器、低频行情与批量历史任务。它需要可靠恢复和业务隔离，但不需要分布式消息系统的复杂度。

## 比较

### 保留 V3.15 多进程体系

优点是不同任务有强进程隔离，未来横向扩容路径直接。缺点是当前机器需要维护大量长期空闲的进程、队列和恢复角色；状态同时分布在数据库与 Redis，诊断和迁移成本高。

### 只合并 Docker 容器

优点是 Compose 看起来更简单。缺点是容器内部仍保留多进程、队列和监督逻辑，资源和状态复杂度没有真正减少，只是隐藏起来。

### PostgreSQL 任务加一个普通后台

优点是任务、租约、检查点和请求额度只有一个真实来源；常驻组件少，恢复路径可直接查询，业务任务不再被机械拆成数千个调度对象。缺点是普通后台成为主要执行组件，需要严格限制单次调用、数据库连接和任务并发；未来多机扩展前要重新评估任务领取方式。

## 决定

采用第三种方案：常驻组件固定为前端、API、普通后台和 PostgreSQL。普通后台内置 Cron、任务领取、采集、通知和恢复。策略验证、目标计算及回测中的不可信代码继续使用按需创建的一次性强隔离沙箱。

PostgreSQL 保存任务状态、优先级、租约、围栏令牌、检查点、数据源请求预算和熔断状态。实时、当日日线、普通业务和大批量任务通过优先级、执行槽和预留请求额度隔离，不再通过常驻 Worker 隔离。

全市场当日日线是一个业务任务。Provider 根据真实能力决定单次、分页、分组或任务内部逐股请求；系统保存任务内游标和失败清单，不生成数千个通用单股任务。

## 安全和可靠性边界

- 普通后台中的每次外部调用、数据库批次和业务步骤必须有截止时间与失败隔离。
- 领取任务使用数据库租约和围栏令牌，迟到结果不能覆盖新执行。
- 任务在安全点保存检查点，进程重启后只能从已提交位置继续。
- 所有 Provider 请求先原子领取持久额度，手工、重试和探测不能绕过。
- 用户策略仍无网络、数据库、密钥和宿主文件访问权限，沙箱超时后必须销毁。
- 数据库不可用时不在内存创建正式任务、调度事实或通知投递结果。

## 兼容、迁移和回退

迁移按 `docs/development/v4-simplified-architecture-migration.md` 执行。旧 `job_run`、`job_item`、`event_outbox` 和 RQ 标识先只读保留，不立即删除。切换前备份数据库和卷；切换期间禁止旧体系创建新任务。

每阶段都以数据库迁移和 Compose 版本为回退点。若新后台未通过恢复、额度或关键业务验收，停止新后台并恢复上一版应用；不得回滚已经成功提交的业务数据。只有完成一个观察期并核对数据后，才可删除 Redis 卷、旧镜像和废弃表。

## 验证要求

- 文档基线、迁移清单和实现使用相同状态、表和组件名称。
- 最终 Compose 只有四个常驻组件，且不存在隐藏的旧任务消费者。
- 模拟后台重启、租约过期、额度耗尽、数据源切换和单股失败，验证任务能恢复且不会重复写入。
- 核对管理员、配置和全部正式业务数据迁移前后数量与关键校验和。
