# PRD: LongInvest 简化架构

## 1. 概述

LongInvest 面向单个管理员，提供 A 股行情获取、目标价格计算、历史回测、股票监控和通知，不执行自动交易。

当前实现把任务分发、异常恢复、定时调度、维护和不同队列分别做成常驻进程，并把全市场当日日线拆成数千个单股任务。这超过了单用户、单服务器场景的实际需要，增加了内存、运行时间和维护成本。

本次改造保留现有业务数据和用户可见能力，重新收敛模块、任务机制和部署结构。

## 2. 目标

- 将系统整理为清晰的基础、数据库、用户、数据、策略与监控、回测、通知、API 和前端边界。
- 删除 Redis/RQ、任务分发器、看门狗、维护进程和进程监督器。
- 常驻运行组件收敛为前端、API、普通后台和 PostgreSQL。
- 让全市场当日日线作为一个业务批次执行，并按数据源能力分页、分组或逐股采集。
- 为所有数据源提供统一的频率、并发和每日请求额度保护。
- 保留任务进度、失败隔离、有限重试、重启恢复和审计能力。
- 降低常态内存和批量采集耗时。

## 3. 模块边界

### 3.1 基础模块

负责日志、配置、模块公开接口、Cron 定时器、简单任务状态和健康检查。

模块间同步操作直接调用公开 Service；采集、回测和通知等耗时操作写入 PostgreSQL 任务表，由普通后台领取。系统不建设通用消息总线。

### 3.2 数据库基础层

负责 SQLAlchemy 基础配置、连接、事务、迁移、分页、批量插入、批量更新和冲突处理工具。

数据库基础层不拥有业务表，也不提供绕过业务规则的通用外部写接口。每个业务模块维护自己的表、字段、查询和写入规则。

### 3.3 用户中心

负责单个管理员的登录、退出、修改密码、Session 查询和 Session 撤销。不支持多用户、角色和租户。

### 3.4 数据获取模块

负责股票清单、实时行情、全市场当日日线、历史 K 线、复权数据、质量校验和多数据源适配。

每种数据能力独立配置主源、备用源、最小请求间隔、最大并发、每日请求上限、单次允许数量、额度重置时间和是否允许自动切换。

### 3.5 策略与监控模块

负责多策略管理、代码版本、统一参数、发布与回滚、目标价格区间、监视列表和真实行情信号。

所有策略使用统一输入和四档目标价格输出。正式信号只使用已发布策略、有效目标和真实行情。

### 3.6 回测模块

负责调用策略，以训练期计算一次目标价格，再用测试期数据模拟收益、回撤、交易次数等结果。支持单股、监控列表和全市场回测。

回测可以产生候选股票，但不得自动加入监视中心、修改正式目标或发送正式通知。管理员可以单只或批量确认候选股票后加入监视中心。

### 3.7 通知模块

提供一个统一通知入口，下接邮件、企业微信和飞书适配器。负责模板、渠道选择、发送记录、有限重试和重复发送保护。

通知模块只发送其他模块已经确认的业务通知，不负责计算价格信号。

### 3.8 API 层

负责身份和 CSRF 校验、参数校验、调用模块公开接口、分页和统一响应。API 层不直接操作业务表，不包含业务判断。

### 3.9 前端

保留中文页面、主题、行情图表、任务进度、策略、回测、监控和通知管理。前端只调用 API，不直接访问数据库和第三方服务。

## 4. 用户故事

### US-001: 简化运行基础

**描述：** 作为管理员，我希望系统只运行必要组件，以降低资源占用和故障点。

**验收标准：**

- [ ] 常驻组件只有前端、API、普通后台和 PostgreSQL。
- [ ] Redis/RQ、任务分发器、看门狗、维护进程和进程监督器不再参与运行。
- [ ] 普通后台异常退出后由 Docker 重启，并继续处理未完成任务。
- [ ] 相同 Cron 时间点只能创建一个业务批次。
- [ ] 健康页面能区分 API、普通后台、数据库和外部数据源状态。

### US-002: 数据库公共能力

**描述：** 作为开发者，我希望共享可靠的事务和批量操作能力，同时让业务表仍由所属模块维护。

**验收标准：**

- [ ] 数据库基础层提供连接、事务、迁移、分页和批量写入工具。
- [ ] 每个业务表有唯一所属模块。
- [ ] 业务模块不能通过通用接口修改其他模块的数据。
- [ ] 批量写入在任一批次失败时有明确回滚或部分成功规则。
- [ ] 现有正式数据迁移后数量和关键约束一致。

### US-003: 全市场当日日线

**描述：** 作为管理员，我希望交易日 17:00 高效获取完整的全市场当日日线。

**验收标准：**

- [ ] 一个交易日只创建一个全市场业务任务。
- [ ] 不为每只股票创建独立业务任务记录。
- [ ] 数据源支持批量时使用分页或分组请求。
- [ ] 数据源只支持单股时在同一业务任务内保存分组检查点。
- [ ] 行情逐股校验，数据库按批写入，只对缺失或失败股票重试。
- [ ] 页面显示预计请求数、总股票数、成功数、缺失数、失败数和当前阶段。
- [ ] 单股失败不会回滚其他有效日线。

### US-004: 数据源请求预算

**描述：** 作为管理员，我希望系统遵守不同数据源的请求限制，避免账号或 IP 被限制。

**验收标准：**

- [ ] 每个数据源可以配置每日请求上限、最小间隔和最大并发。
- [ ] 自动、手动、重试和探测请求共同消耗额度。
- [ ] 请求发出即计数，超时或失败不退回额度。
- [ ] 配置每日 50000 次后，第 50001 次请求在本地被阻止。
- [ ] 多个同时请求不能让总计数超过上限。
- [ ] 服务重启后保留当天已用额度。
- [ ] 页面显示已用、剩余、重置时间和限流原因。
- [ ] 实时行情和当日日线优先于历史回填使用额度。

### US-005: 多数据源切换

**描述：** 作为管理员，我希望不同数据能力可以选择不同数据源，并在允许时自动切换。

**验收标准：**

- [ ] 股票清单、实时行情、当日日线、历史日线和复权分别配置路由。
- [ ] 主源整体连接失败、限流或额度耗尽时可以切换备用源。
- [ ] 主源部分缺失时只使用备用源补缺。
- [ ] 每条正式数据记录真实来源。
- [ ] 同一股票同日来源冲突进入质量检查，不静默覆盖。
- [ ] 管理员可以固定数据源，但不能突破请求限制。

### US-006: 策略版本和统一输出

**描述：** 作为管理员，我希望管理多个策略，同时保持参数和目标价格输出一致。

**验收标准：**

- [ ] 策略支持草稿、验证、发布和回滚。
- [ ] 发布版本不可修改并绑定代码和参数哈希。
- [ ] 参数按统一 Schema 校验。
- [ ] 所有策略输出四档有序目标价格和诊断摘要。
- [ ] 策略在无网络、无数据库凭据的按需隔离容器中执行。
- [ ] 隔离容器在任务完成或超时后销毁。

### US-007: 回测和候选股票

**描述：** 作为管理员，我希望使用历史数据评价策略，并把合适股票人工加入监视中心。

**验收标准：**

- [ ] 训练期只用于计算目标价格。
- [ ] 测试期只使用训练期产生的目标进行模拟。
- [ ] 结果展示收益、最大回撤、交易次数和失败原因。
- [ ] 候选条件可以按回测指标配置。
- [ ] 候选股票必须经过单只或批量确认才能加入监视中心。
- [ ] 回测不会修改正式目标、正式信号或发送正式通知。
- [ ] 页面可查看任务进度、候选列表和确认结果。

### US-008: 统一通知

**描述：** 作为其他业务模块，我希望用同一种方式发送邮件、企业微信或飞书通知。

**验收标准：**

- [ ] 调用方只提交通知类型、对象、模板参数和幂等键。
- [ ] 邮件、企业微信和飞书分别实现适配器。
- [ ] 单渠道失败不影响其他渠道和原业务提交。
- [ ] 相同幂等键不会产生重复正式通知。
- [ ] 每次发送尝试、结果和安全错误摘要可查询。
- [ ] 通知失败只进行有限重试。

### US-009: 单管理员和兼容 API

**描述：** 作为现有管理员，我希望重构后继续使用原账号、页面和业务数据。

**验收标准：**

- [ ] 现有管理员密码哈希和有效业务数据得到保留。
- [ ] 登录、退出、改密和 Session 撤销保持可用。
- [ ] 现有前端需要的 API 要么兼容，要么在同一批次更新前端。
- [ ] 页面具有加载、空数据、失败和重试状态。
- [ ] 前端生产构建、接口类型检查和浏览器关键流程通过。

## 5. 功能要求

- FR-1: 系统必须使用 PostgreSQL 作为业务数据、任务状态和请求额度的唯一真实来源。
- FR-2: 普通后台必须直接领取 PostgreSQL 中到期任务。
- FR-3: 普通后台必须在领取任务时同时取得有限期执行权。
- FR-4: 普通后台必须在启动和定期扫描时恢复执行权已过期的任务。
- FR-5: Cron 必须通过数据库唯一约束防止重复创建批次。
- FR-6: 全市场当日日线必须表现为一个业务任务。
- FR-7: 数据获取模块必须根据数据源能力生成分页、分组或单股采集计划。
- FR-8: 数据获取模块必须在任务启动前计算预计请求数和额度可用性。
- FR-9: 每次外部数据请求必须经过统一请求预算检查。
- FR-10: 请求预算必须支持数据源总额度和数据能力额度。
- FR-11: 历史回填不得消耗为实时行情和当日日线保留的额度。
- FR-12: 正式行情必须保存数据来源和采集时间。
- FR-13: 数据写入必须使用批量操作并保持价格精度。
- FR-14: 回测候选必须由管理员确认后才能加入监视中心。
- FR-15: 正式通知必须通过通知模块的统一入口创建。
- FR-16: 策略和回测代码必须在按需隔离环境执行。
- FR-17: API 层必须通过模块公开接口完成业务操作。
- FR-18: 迁移过程必须保留现有正式数据和审计历史。

## 6. 主要流程

```text
Cron/手动操作
  -> 创建一个 PostgreSQL 业务任务
  -> 普通后台领取
  -> 计算数据源、请求计划和可用额度
  -> 分页/分组采集
  -> 逐股校验
  -> 批量写入
  -> 只记录并重试缺失项
  -> 完成或部分完成
```

```text
历史数据
  -> 策略训练期计算目标
  -> 测试期回测
  -> 指标筛选候选股票
  -> 管理员确认
  -> 加入监视中心
  -> 真实行情触发正式信号
  -> 统一通知入口
```

## 7. 非目标

- 不支持多用户、角色、租户和组织。
- 不接入券商，不执行自动交易。
- 不建设微服务、消息中间件、服务注册或分布式任务平台。
- 不根据每次请求延迟动态选择最快数据源。
- 不允许管理员突破数据源官方请求限制。
- 不允许回测直接产生正式通知。
- 不为全市场当日日线创建数千个独立业务任务。

## 8. 技术和迁移要求

常驻组件为前端、API、普通后台和 PostgreSQL。策略验证、目标计算和回测按需启动隔离容器，完成后销毁。

简单任务状态包括 `PENDING`、`RUNNING`、`SUCCEEDED`、`PARTIAL`、`FAILED`、`PAUSED` 和 `CANCELED`。任务保存进度、有限重试次数、下次执行时间、执行权到期时间和安全错误摘要。

改造按以下顺序进行：

1. 发布新的生效规格并冻结迁移边界。
2. 建立数据库公共能力和简化任务执行器。
3. 改造全市场当日日线和请求预算。
4. 迁移历史、实时和多数据源能力。
5. 整理策略、回测、监控和通知边界。
6. 切换 Compose，移除 Redis/RQ 和旧后台角色。
7. 完成数据核对、性能测试和服务器验收。

旧任务在切换前停止创建。已完成任务保留为历史；未完成任务按业务类型迁移或明确取消，不允许静默丢失。

## 9. 成功指标

- 常驻应用进程为 API 和普通后台两个。
- 空闲状态 LongInvest 全部常驻容器内存不超过 800 MiB。
- 全市场当日日线期间常驻容器内存不超过 1.2 GiB。
- 支持批量接口的数据源在正常额度下 10 分钟内完成全市场当日日线。
- 只支持单股接口时，任务启动前展示基于额度和速率计算的预计时间。
- 配置每日请求上限后，任何并发、重试和重启场景都不能突破上限。
- 单股或单渠道失败不回滚其他已成功结果。
- 重构后现有管理员和正式业务数据核对一致。

## 10. 已确认决策

- 用户中心第一版只支持单管理员。
- 回测候选必须人工确认后加入监视中心。
- 策略统一输出目标价格区间，回测指标负责筛选候选股票。
- 数据能力分别配置主源和备用源，整体失败切换，部分缺失补缺。
- Redis/RQ 和现有多进程任务基础设施移除。
- 正式代码施工前必须先将本 PRD 转换为新的生效需求基线。

## 11. 待后续数据源调研确定

- 各数据源每种能力的真实批量大小、并发、间隔和每日额度。
- 每个请求限制按 IP、账号、接口还是多个维度共同计算。
- 支持全市场当日日线的具体主源和备用源。

这些值必须通过官方说明和服务器实测确定，不能在 PRD 中凭经验写死。
